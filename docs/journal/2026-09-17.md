## 조치

### 1) PE 버전 리소스 추가 (`res/nexa-coffee.rc`)
버전 정보가 통째로 없는 **작고 · 서명 없고 · CRT도 없는** PE는 ML 휴리스틱의 고전적 오탐 대상이다. 서명이 없는 v1에서 할 수 있는 완화책이 이것이다.

- `VS_VERSION_INFO` 블록: CompanyName · FileDescription · FileVersion · InternalName · LegalCopyright · **OriginalFilename(아키텍처별)** · ProductName · ProductVersion.
- 숫자는 **VERSION 파일 하나에서** 온다 — rc에 손으로 적지 않는다. `Makefile`의 `RCDEF`(`$(subst ., ,$(VERSION))` → `-DCF_VER_MAJOR/MINOR/PATCH`)와 `build.bat`의 `for /f delims=.`가 같은 규약으로 넘긴다. `CF_ARCH64`로 OriginalFilename을 x64/x86으로 가른다.
- 문자열은 전처리기 stringize(`#`)로 만든다. **windres(gcc -E)는 당연히 되고, MSVC `rc.exe`도 지원하는지 이 PC에서 먼저 확인한 뒤** 채택했다(`rc.exe /dCF_VER_MAJOR=0 ... ` → 리소스에 "0.1.1" 박힘).
- 실측: `rc.exe`로 양쪽 아키텍처 컴파일 green(OriginalFilename이 각각 `nexa-coffee-x64.exe`/`-x86.exe`). **MSVC 전체 빌드 30,720 → 31,744 B**(+1,024) — 예산 64 KB의 절반 이하. 임베드 확인:
  `CompanyName=SosomLab · ProductName=Nexa Coffee · FileVersion=0.1.1 · OriginalFilename=nexa-coffee-x64.exe`
- mingw(windres) 크로스 빌드와 크기 예산은 이 PC에 mingw/make가 없어 **CI로 확인**(CLAUDE.md 규약).

### 9) v0.1.1 릴리스(run 35179731098) — 릴리스는 성공, 제출 잡 2개가 실패했고 **둘 다 진짜 버그였다**

| 잡 | 결과 |
| --- | --- |
| meta · linux-windows · macos · publish | ✅ 자산 5개 + SHA256SUMS · GitHub Release 공개 |
| homebrew / tap | ✅ 탭 0.1.1 갱신 |
| windows-packages / winget | ❌ `매니페스트 생성 + 검증` |
| windows-packages / chocolatey | ❌ `choco push` → **403 Forbidden** |

**(a) choco 가드가 모더레이션을 못 알아봤다.** 가드는 "직전 버전이 공개 피드에 `<entry>`로 있는가"로 판정했는데,
**chocolatey 피드는 미승인 버전도 `<entry>`로 돌려준다**:

```
d:Version>0.1.0   d:IsApproved>false   d:PackageStatus>Submitted
```

그래서 0.1.0이 모더레이션 중인데도 `choco 제출: true`가 되어 0.1.1을 밀었고 **403**을 받았다.
→ 판정을 `<d:IsApproved ...>true</d:IsApproved>` 로 바꿨다. 실제 피드 대조: `nexa-coffee 0.1.0 → not approved` · `git 2.47.1 → APPROVED`.

**(b) `winget validate`의 exit 40은 경고다.** 스키마 헤더를 넣었더니 이번엔 다른 경고가 났다:

```
Manifest Warning: The schema header URL does not match the expected pattern.
  Value: # yaml-language-server: $schema=https://aka.ms/winget-manifest.installer.1.12.0.schema.json
```

같은 파일이 **이 PC의 winget 1.29.290에서는 경고 없이 exit 0**이고(CRLF로 바꿔 봐도 통과),
PR #433980의 komac 매니페스트도 **같은 URL**을 쓰며 Microsoft 검증을 통과했다 → 러너의 winget이
우리 `ManifestVersion: 1.12.0`보다 오래된 것이다. 경고 때문에 파이프라인이 죽을 이유가 없으므로
**40은 `::warning::`으로 기록만 하고 통과**시키고, 그 외 코드만 실패로 본다. 진단이 쉽도록 `winget --version`도 찍는다.

### 11) 🔴 `WINGET_TOKEN`에 `workflow` 스코프가 없다 (사용자 조치 필요)
자동 제출이 실패한 마지막 고리. `wingetcreate submit`은 우리 포크 master가 upstream과 어긋나면 거부하는데
(**09-17 기준 1,663 커밋 뒤처짐** — upstream은 릴리스 사이에 수천 커밋 나아간다), 동기화 단계를 넣었더니:

```
refusing to allow a Personal Access Token to create or update workflow
`.github/workflows/domain-validation-assist.lock.yml` without `workflow` scope (HTTP 422)
```

upstream 커밋이 `.github/workflows/`를 건드리므로 **포크 동기화에는 `workflow` 스코프가 필요**하다.
이번 0.1.1 PR은 그래서 **포크 동기화 없이** 만들었다 — 포크 master에서 브랜치를 따고 contents API로 매니페스트
3개만 올린 뒤 PR(우리가 건드리는 경로는 `manifests/…` 뿐이라 workflow 스코프가 필요 없다). PR은 MERGEABLE이다.
→ 다음 릴리스부터 자동화가 돌게 하려면 **PAT에 `workflow` 스코프 추가**(T-17).

### 12) T-17 해소 — `WINGET_TOKEN`에 `workflow` 스코프 추가됨 (사용자 조치)
사용자가 **기존 classic PAT의 스코프만 수정**했다(값 그대로 → 시크릿 재등록 불필요 · 실제로 시크릿 `updated_at`이
09-12 그대로다). 확인은 두 경로가 일치했다:

```
(사용자 로컬 curl)  X-OAuth-Scopes: repo, workflow
(워크플로 진단)      WINGET_TOKEN 스코프: repo, workflow  ·  ✓ workflow 있음
```

**동작 확인**(run 35185267574 · 전 잡 success): `Successfully fetched and fast-forwarded from upstream microsoft:master`
→ 포크가 upstream과 **identical**(직전엔 1,672 커밋 뒤처져 있었다).

재발 방지로 워크플로를 둘 고쳤다.
- 가드의 "스위치 상태"에서 **`x-oauth-scopes` 헤더로 스코프를 찍는다**(토큰 값은 노출하지 않는다) — 릴리스가 죽고 나서야 알 이유가 없다.
- 포크 동기화를 `winget_go` 대신 **토큰 유무**로 건다. fast-forward라 부작용이 없고, 제출을 건너뛰는 실행에서도 맞춰 둬야 다음 제출 때 또 벌어지지 않는다.
